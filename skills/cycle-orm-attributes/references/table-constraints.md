# Table-level constraints: Index, PrimaryKey, ForeignKey

Table-level attributes: indexes, composite PK, FK without a relation wrapper.

See also:
- `#[Table]` lives on the class → `define-entity.md`
- PK via `type: 'primary'` vs composite → `column-types.md`
- automatic FKs via relations (HasOne/BelongsTo/...) → `relations.md`

---

## `#[Table]` — wrapper around the whole table level

```php
use Cycle\Annotated\Annotation as Cycle;
use Cycle\Annotated\Annotation\Table;
use Cycle\Annotated\Annotation\Table\Index;
use Cycle\Annotated\Annotation\Table\PrimaryKey;

#[Cycle\Entity]
#[Table(
    columns: [/* class-level style; see define-entity.md */],
    primary: new PrimaryKey(columns: ['tenant_id', 'sku']),
    indexes: [
        new Index(columns: ['tenant_id']),
        new Index(columns: ['tenant_id', 'code'], unique: true),
        new Index(columns: ['create_time'], name: 'idx_products_created'),
    ],
)]
class Product { /* ... */ }
```

Three parameters:
- **`columns:`** — array of `#[Column]`s (class-level column declaration).
- **`primary:`** — composite PK via `PrimaryKey`.
- **`indexes:`** — array of `Index`es.

`#[Table]` itself is **not required**. If there are no indexes / composite PK / class-level columns — `#[Table]` can be omitted entirely, `#[Entity]` is enough.

## `#[Index]` — indexes

```php
new Index(
    columns: ['email'],          // required: field names (mapped to their columns) or column names; 'createTime DESC' sets sort order
    unique: false,               // default false
    name: 'idx_users_email',     // default = generated by Cycle
)
```

**The `#[Index]` attribute is repeatable** — can be declared multiple times. It can also be placed **directly on the class** (not only inside `#[Table]`):

```php
#[Entity]
#[Index(columns: ['email'], unique: true)]
#[Index(columns: ['tenant_id', 'create_time'])]
class User { /* ... */ }
```

**Class-level** is more convenient with property-style column declaration (`define-entity.md`).

### Unique indexes

```php
#[Index(columns: ['email'], unique: true)]
```

For a composite unique:
```php
#[Index(columns: ['tenant_id', 'sku'], unique: true)]
```

— a unique pair `(tenant_id, sku)`. Within one tenant, sku is unique.

### When to set `name:`

Typically — don't. Cycle generates the name automatically by convention. The name is needed explicitly if:
- your migrations are diffed by an external tool and name stability matters,
- you want to DROP INDEX by name from the application,
- you need the same name in every environment — the generated one contains a random `uniqid()` part (see below).

## `#[PrimaryKey]` — composite PK

`#[PrimaryKey]` is a subclass of `#[Index]` with unique=true and a fixed name `'PK'`. Place it inside `#[Table(primary: ...)]` or directly on the class — both work, with or without `#[Table]`. Its `columns:` take **column names**, not field names: `columns: ['tenantId']` for a property mapped to `tenant_id` fails with `FieldException`: "Undefined field with column name `tenantId`."

```php
#[Entity]
#[Table(
    primary: new PrimaryKey(columns: ['tenant_id', 'sku']),
)]
class Product
{
    #[Column(type: 'int')]
    public int $tenant_id;
    #[Column(type: 'string')]
    public string $sku;
    #[Column(type: 'string')]
    public string $name;
}
```

**Rules:**
- Columns in PrimaryKey are declared as ordinary (`int`/`string`), **not** `primary` or `bigPrimary` — otherwise they become auto-increment.
- A composite PK in STI/JTI works, but **rarely** makes sense; PK is usually single for an Entity.

### `Table(primary: PrimaryKey)` vs multiple `Column(primary: true)`

A composite PK can be set **two equivalent ways**: via `Table(primary: PrimaryKey(columns: [...]))` (as above) or via `primary: true` on each column:

```php
#[Entity]
class Product
{
    #[Column(type: 'int',    primary: true)]
    public int $tenant_id;
    #[Column(type: 'string', primary: true)]
    public string $sku;
}
```

Both options produce the same schema. Cycle cross-checks both sources at `getPrimaryFields()`:
- one of the declarations is empty — the other is taken;
- both match — ok;
- both differ — `EntityException`: "Ambiguous primary key definition for `role`."

Pick one style per project (see `column-types.md`).

## `#[ForeignKey]` — manual FK

Most FKs are created automatically through relations (`HasOne`/`BelongsTo`/... with `fkCreate: true`). But sometimes an FK is needed **without** a relation:
- FK to a "reference" table that you don't traverse via an ORM relation,
- FK from composite columns hard to describe via a relation.

```php
use Cycle\Annotated\Annotation\ForeignKey;

#[Entity]
#[ForeignKey(
    target: Currency::class,         // role or class of a registered entity
    innerKey: 'currency_code',       // own field or column
    outerKey: 'code',                 // field or column in target; default = PK
    action: 'CASCADE',                // 'CASCADE' | 'NO ACTION' | 'SET NULL'; default 'CASCADE'
    indexCreate: true,                // create an index on innerKey
)]
class Price
{
    #[Column(type: 'primary')]
    public int $id;
    #[Column(type: 'string', length: 3)]
    public string $currency_code;
}
```

`target:` must resolve to an entity in the schema; any other name fails with `RegistryException`: "Undefined entity `name`". When `outerKey` is not the target PK, Cycle adds a UNIQUE index on the target columns itself (unless an index on them already exists).

**The attribute is repeatable** — multiple `#[ForeignKey]`s can be declared on a single class. It can also be placed **on a property** (then `innerKey` is inferred from the property name, see below).

### Property-level

```php
#[Column(type: 'string', length: 3)]
#[ForeignKey(target: Currency::class, outerKey: 'code')]
public string $currency_code;
```

— on the property `innerKey` defaults to the property name.

### When `#[ForeignKey]` vs FK via relation

| Scenario                                                       | What to use               |
|---------------------------------------------------------------|---------------------------|
| You need the link in code too (`$order->customer`)             | `#[BelongsTo]` (`relations.md`) — the FK will be created automatically |
| There's an FK, but you don't navigate to the target object in code | `#[ForeignKey]` without a relation |
| Composite FK across multiple columns                           | `#[ForeignKey(innerKey: [...], outerKey: [...])]` |

## Names of indexes and FKs: what Cycle generates

The generated name is `{table}_index_{columns}_{uniqid()}` for indexes and `{table}_foreign_{columns}_{uniqid()}` for FKs; a name longer than 64 characters is replaced with its `md5()` (`AbstractTable::createIdentifier()`). So names never exceed identifier limits, but they are **not deterministic**: a fresh schema build in another environment produces different names.

**Don't rely on a specific generated name** when writing migrations by hand. If migrations are via `cycle/migrations` — it'll handle it. If you write by hand — set `name:` explicitly.

## Common pitfalls

- **Composite PK with `type: 'primary'` columns** — auto-increment + composite PK conflict. In a composite PK, columns must be ordinary (`int`/`string`/...).
- **`#[Index]` with an empty `columns:`** — `AnnotationException`: "Invalid index definition for `role`. Column list can't be empty." List at least one column.
- **Changing column order in an index** requires recreating the index in a migration — it's a **different** index from the query planner's perspective.
- **`#[ForeignKey]` `innerKey`/`outerKey` that is neither a field nor a column** — schema build fails with `AnnotationException`: "Unable to resolve column name."
- **`action: 'SET NULL'` on an FK + non-nullable column** — crashes when trying to SET NULL. The column must be `nullable: true`.
- **CASCADE FK on an MSSQL identity column** — forbidden by SQL Server itself. Use `'NO ACTION'` or `fkCreate: false`. See `cycle-orm/references/schema-troubleshooting.md`.

## Checklist

1. Unique business keys (email, slug, sku within tenant) are protected with `unique: true`.
2. Composite PK via `#[Table(primary: new PrimaryKey(...))]`; ordinary columns inside it — not `primary`/`bigPrimary`.
3. FKs via relations (`relations.md`) are preferable to `#[ForeignKey]` — if you navigate to the target entity in code.
4. `#[ForeignKey]` with `action: 'SET NULL'` — the corresponding column is nullable.
